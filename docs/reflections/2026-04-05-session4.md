# Reflexion — 2026-04-05 (sesion 4)

## Que se hizo
- D7: Frontend dashboard Damian — 3 widgets React (TodayAppointmentsWidget, StalePatientWidget, UpcomingAppointmentsWidget) consumiendo endpoints dedicados
- D8: Integracion musica+chat — MusicContext compartido via React Context, agente IA controla Ambient player (play/pause/next con busqueda fuzzy por nombre)
- Demo tracks: auto-descarga de 3 tracks relajantes de Mixkit (royalty-free) al IndexedDB la primera vez que se abre Musica Ambiente

## Que salio bien
- Los 3 endpoints del dashboard ya estaban listos del backend (sesion 3), la implementacion frontend fue directa
- MusicContext con React Context fue la solucion mas simple y efectiva para comunicar Agent y Ambient
- Decision de usar Mixkit CDN en vez de guardar MP3 en el repo evita ocupar storage de Render
- IndexedDB como cache funciona perfecto: primera carga descarga, despues todo local
- 136 tests pasando (incluso se resolvieron los 2 que fallaban en zenco)
- Build frontend limpio sin errores TypeScript en todos los cambios

## Que salio mal
- Sub-agentes no funcionaron en esta sesion — el contexto del sistema (MCP tools de PostHog, Slack, Supabase, etc.) es demasiado grande y causa "Prompt is too long" en todos los agentes (Explore, general-purpose, haiku)
- Se perdieron ~5 minutos intentando diferentes configuraciones de sub-agentes antes de aceptar que el contexto MCP era el problema

## Lecciones aprendidas
- Cuando hay muchos MCP tools conectados, los sub-agentes no pueden funcionar por limite de contexto. Alternativa: trabajar directo con Read/Grep/Glob para investigacion y reservar agentes solo para tareas de implementacion aisladas
- El approach de "no guardar assets en el repo, descargar de CDN y cachear en IndexedDB" es ideal para apps desplegadas en Render free tier
- React Context es suficiente para comunicacion entre componentes hermanos (Agent y Ambient) — no necesita EventBus ni estado global mas complejo
